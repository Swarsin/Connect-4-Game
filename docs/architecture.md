# Architecture

## Layout

```
src/c4/
  engine/      bitboard rules, encoding (planes), symmetry, notation
  agents/      Agent protocol, Random, Minimax, UCT MCTS, solver, AlphaZero
  solver/      wrapper around Pascal Pons' c4solver (evaluation only)
  alphazero/   config, network, PUCT MCTS, self-play, trainer, checkpoints, tracking
  eval/        arena, Elo, benchmarks, batched network evaluation, CLI
  export/      ONNX export, parity checks, int8/fp16 quantisation
tests/         engine vs reference implementation, agents, eval, AlphaZero, resume
scripts/       data generation, solver build, benchmarks
configs/       YAML training configs (main / smoke / local / ablations)
web/           TypeScript + React site (Vite); engine port, ONNX inference, UI
```

## Engine

`engine/board.py` uses the standard bitboard layout: 7 columns of 7 bits (6 rows + a sentinel
top bit), bit index `col * 7 + row` with row 0 at the bottom. A move is
`current ^= mask; mask |= mask + bottom[col]`, undo is its inverse. Win checks are four
shift-and-AND tests; "winning cells" uses the Pons trick. A position is identified by
`current + mask`; the mirror key is the minimum with the mirrored position (used to de-duplicate
benchmarks).

Measured with `scripts/bench_engine.py` (Linux, CPython 3.12, same machine):

| workload | bitboard | legacy stack board | speed-up |
|---|---|---|---|
| random self-play games / s | 21,408 | 2,051 | 10.4x |
| search node (copy + play) / s | 1,027,823 | 26,787 | 38.4x |

The copy+play number is the one that matters for Minimax: the legacy implementation deep-copied
a board of `Stack` objects at every search node.

Correctness is covered by a naive 2D-list reference implementation, 10,000 Hypothesis-generated
move sequences and 5,842 shared fixture positions (`data/fixtures/engine_cases.json`) which the
TypeScript engine must reproduce exactly.

## Classic agents

* **Minimax** — negamax + alpha-beta, transposition table keyed by `board.key()`, centre-first
  move ordering, mate-distance scoring, immediate-win shortcut. The heuristic is symmetric across
  the 69 windows of four cells (the legacy version scored only the AI's own lines) and includes a
  centre-column term.
* **UCT MCTS** — iteration-limited (reproducible), values alternate perspective correctly, the side
  to move comes from the board (no shared mutable player objects), tree reuse via `advance`, and an
  optional "finish/blocks immediate wins in rollouts" mode.

Legacy bugs fixed in both bots are listed in `docs/evaluation.md`.

## Evaluation

* **Perfect-play benchmarks** — Pascal Pons' solver labels every move of every benchmark position;
  we report *optimal move* (max score) and *result-preserving move* (same win/draw/loss outcome) by
  game stage, plus the network's value accuracy when available.
* **Elo** — Bradley–Terry fit over all recorded games with bootstrap confidence intervals,
  anchored at `random = 0`; draws count as half a win.
* **Arena** — every opening is played with both colours (49 two-move openings = 98 games; the
  default 7 one-move openings = 14 games).

Baseline Elo (3,528 games, `results/elo/`) and benchmark tables (`results/README.md`) are
regenerated by `python -m c4.eval.cli report`.

## AlphaZero

* **Network** (`alphaZero/network.py`) — 3x3 stem + N residual blocks (2 conv-BN-ReLU each),
  policy head (1x1 conv -> 2x42 -> 7 logits) and value head (1x1 conv -> 42 -> 64 -> 1 -> tanh).
  Main config: 128 channels x 10 blocks, 2.96M parameters (~12 MB fp32).
* **Search** (`alphaZero/mcts.py`) — PUCT with `Q + c_puct * P * sqrt(sum N) / (1 + N)`, first-play
  urgency for unvisited moves, Dirichlet noise at the root, virtual-visit-free batched descent.
  Simulations are run over **many trees in lockstep**: one simulation step per tree, all leaves
  evaluated in a single network call. The same code path serves self-play, benchmarking and single
  positions.
* **Self-play** (`alphaZero/selfplay.py`) — G games per worker are advanced in lockstep; tree reuse
  between moves; temperature 1 for the first 12 plies then 0; samples store planes (uint8), the
  visit distribution, the game result and the root search value. Horizon = 1000 positions, 50%
  horizontal mirror augmentation at training time.
* **Training** — SGD + momentum (AdamW supported), step LR schedule, AMP, gradient clipping,
  policy cross-entropy + value MSE, `sample_reuse=6` gradient steps per new position. Pydantic
  configs with YAML `extends`.
* **Checkpointing** (`alphaZero/checkpoint.py`) — atomic save of model + optimiser + scaler + RNGs +
  counters + replay buffer (`state.pt`, `buffer.npz`), weights-only snapshots every iteration,
  retention `keep_last=3` + every 10th, W&B artifact upload, wall-clock budget so a Kaggle session
  stops cleanly before the 12 h limit. `--resume auto` restores everything and continues the
  W&B run.

### Inference optimisation

Small batches on a GPU are dominated by kernel-launch overhead (~70 tiny kernels per forward).
`alphaZero/inference.py` builds a snapshot with BatchNorm folded into the convolutions, runs fp16
and captures one **CUDA graph per batch-size bucket** (powers of two).
On an RTX 3070 with the 128x10 network, 200 simulations, 128 parallel games per worker:

| inference path | games/hour (1 worker) |
|---|---|
| eager fp32 + autocast | 5,878 |
| BN-folded fp16 + CUDA graphs | 12,835 |

Four self-play workers: **40,784 games/hour, ~55k simulations/second** (`scripts/bench_selfplay.py`).
The Kaggle target is 5,000 games/hour; the local figure is ~8x above it (Kaggle CPUs are
slower, so a Kaggle number still needs measuring).

## Web app

Vite + React + TypeScript, direction "Modern toy" (tokens in `web/src/styles/tokens.css`).

* `web/src/engine/board.ts` is a straight port of the Python bitboard semantics (row 0 at the
  bottom, planes `[2,6,7]`, 1-indexed move strings). It is validated against all 5,842 shared
  fixture positions by `web/tests/engine-parity.test.ts`.
* Classic search runs in a Web Worker (`web/src/ai/worker.ts`): Minimax (negamax + TT + symmetric
  heuristic) and UCT MCTS, both ports of the Python agents. The main thread never blocks; requests
  are promise-based (`web/src/ai/client.ts`) and the worker returns both a move and an analysis
  (visit distribution or score vector) used for the eval bar and top-moves panel.
* State is a move string plus settings; the URL hash carries the position, opponent and mode, so
  every position is shareable and reloadable.
* The win-probability bar is *labelled as an estimate*: Minimax feeds it exact per-move scores
  (full-window search, capped at depth 6) mapped through a logistic scaled to heuristic units;
  MCTS feeds the rollout score of the move it would play. Mate scores map to 0/100. The calibrated
  source will be the AlphaZero value head once the model runs in the worker.
* Visual QA is scripted: `web/scripts/shoot-app.mjs` captures desktop, mobile, dark and terminal
  states into `docs/figures/app-*.png`.

AlphaZero runs in the same worker:

* `web/src/ai/puct.ts` is a line-for-line port of the Python PUCT loop (selection, virtual-loss-free
  single-leaf evaluation, backup signs, lowest-index tie-break), compared against the Python
  reference on 50 positions: **50/50 identical moves** at 200 simulations.
* `web/src/ai/az.ts` loads the static-int8 ONNX model with ONNX Runtime Web (`wasm`, one thread),
  masks illegal columns, and computes the policy in float64. Policy/value match the Python export
  within 5e-3 on 50 fixture positions.
* The value head drives the win-probability bar for AlphaZero levels (labelled `alpha0 · network
  value`); classic bots keep their own estimates. Model loading is lazy and cached per URL.
* Measured in Chromium wasm on this machine: Medium (policy only) ~60 ms, Hard (200 sims) ~1.2 s,
  Master (800 sims) ~3.2 s per move; the first analysis adds ~0.7 s for the 3 MB model.

The ONNX runtime's 14.8 MB wasm file is served from `public/ort` and only fetched when an AlphaZero
level is selected; `vite.config.ts` uses the `onnxruntime-web-use-extern-wasm` export condition to
stop Rollup inlining a duplicate.
